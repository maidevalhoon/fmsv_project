# ATPG Data Pipeline and Intermediate Files

This document provides a detailed breakdown of the data flow in our ATPG project, explaining why each intermediate file format is used and how it is generated.

## 1. The Verification Flow

The overall task of ATPG is mathematical verification. We start with code (`.v`), convert it into physical logic gates (synthesis), parse those gates into a language python understands (`.json`), and finally convert that network of logic into pure mathematical formulas (`cnf`) that a SAT solver can natively evaluate.

```mermaid
graph TD
    A[circuit.v (RTL)] -->|Yosys Tool| B[c17_netlist.v (Gate-Level Verilog)]
    A -->|Yosys Tool| C[c17_tech.json (Gate-Level JSON)]
    B -->|Human Reference| D[Debugging / Visualization]
    C -->|circuit_loader.py| E[Python In-Memory Graph]
    E -->|cnf_builder.py| F[CNF Clauses In-Memory]
    F -->|Glucose3| G[SAT Solver Result]
```

## 2. Why is `c17_netlist.v` created?
*   **What it is:** Synthesized Verilog. It represents the exact same logic as `c17.v`, but translated from abstract boolean statements (like `assign Y = A & B`) into concrete standard cell gates (like `AND2_X1`).
*   **How it is generated:** It is generated by the **Yosys synthesis tool** via the `write_verilog benchmarks/netlists/c17_netlist.v` command inside the `synth/synth.ys` script.
*   **Use case:** It is primarily a **human-readable reference file**. It allows us to view exactly which hardware logic gates Yosys decided to use, to draw circuit diagrams, and it serves as a fallback input format for other specialized hardware tools.

## 3. Which function creates the `.json` file?
*   **Creation:** The JSON file (`benchmarks/json/c17_tech.json`) is **not** created by any Python function in our codebase.
*   **How it is generated:** Like the netlist, it is generated directly by **Yosys** through the `write_json benchmarks/json/c17_tech.json` command in `synth/synth.ys` (or `synth.tcl`).
*   **Use case:** It contains the exact same gate-level information as `c17_netlist.v`, but structured in a dictionary format. Parsing a full Verilog file in Python from scratch is incredibly difficult (requiring complex regex and grammar parsing). Parsing JSON, however, is natively supported in Python with 1 line of code (`json.load(f)`), allowing our `core/circuit_loader.py` to easily convert the circuit into Python objects.

## 4. What is the use of the CNF form?
*   **What it is:** Conjunctive Normal Form (CNF) is a mathematical representation of logic. A circuit gate is converted into a series of boolean compliance rules called "clauses".
*   **Use case:** The SAT solver engine we use (Glucose3 / PySAT) **cannot read Verilog or JSON**. It only understands raw Boolean logic in standard CNF format. Every logic gate, structural wire constraint, and fault assumption must be converted to CNF via the Tseitin transformation (`core/cnf_builder.py`) so the solver can prove whether a test vector exists.

## 5. Why is the CNF file not generated to disk by default?
*   **The Problem:** In our system, the CNF formulation is generated directly **in memory** and passed to the SAT solver dynamically.
*   **Why avoid disk:** A typical circuit has thousands of gates generating tens of thousands of clauses. Generating these numbers as strings, writing them to a massive file on the hard drive, and then immediately forcing the SAT solver to read that file back into memory creates a huge **Disk I/O bottleneck**. 
*   **Performance:** Since ATPG requires doing this process sequentially for hundreds or thousands of faults, writing the CNF to disk would slow down our tool by orders of magnitude. Using Lists of Integers in RAM allows for lightning-fast execution.

## 6. Sample CNF Generation (Proof of Concept)
To demonstrate what the generated data actually looks like, running our system automatically extracts the **in-memory Miter formulation** of an active fault to disk in standard DIMACS format.

**Sample File:** `benchmarks/cnf/c17/SA1_net6.cnf`

This sample corresponds to computing **SA1@net6** on **c17** (ran via `python run_atpg.py --circuit c17 --tech --net 6 --val 1`) and looks like this:
```txt
c Miter CNF for c17 fault SA1@net6
p cnf 28 62
1 2 0
-1 -2 0
3 4 0
-3 -4 0
...
16 0             <-- This is the forced SA1 fault injected purely as logic
...
```
* **Variables (28):** Each integer represents a wire in the circuit (Lines 1-13 Good copy, 14-26 Faulty copy, 27-28 output comparators).
* **Clauses (62):** Each line ending in `0` is an OR constraint that must be satisfied. 
* **The Fault:** The clause `16 0` literally translates directly to: *"Wire #16 (faulty net6) MUST be 1 (TRUE)"*.
